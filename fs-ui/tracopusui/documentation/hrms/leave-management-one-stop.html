1. How to open leave for the first time

ℹ️
Two doors
Employees / managers use People → Leave management (/people/leaves). HR admins configure first under Admin → Leave admin and Admin → Employee leave config. If the menu is missing, flags or role modules are off (see §3).

Employee / manager path

  1. Sign in

    Use an account on a team where leave is enabled.

  2. Open People → Leave management

    Direct URL: /people/leaves (legacy /hrms/leaves redirects here).

  3. Confirm balances appear

    Balance cards show PL/CL/SL (and specials). Empty cards usually mean opening balances were never imported and accrual has not run yet — not a UI bug.

  4. Apply

    Use Apply leave / create drawer: pick type, dates, half-day if needed, notes/docs, then submit.

Admin first-time path (before anyone applies)

  1. Application Config — turn on org + role leave flags (§3).
  2. Global Policy Center — publish a policy (§4–5).
  3. Holidays + working-day rules (§8).
  4. Employee leave config — dry-run OB import, then live (§9–10).
  5. Enable schedulers ACCRUAL / CF / COMP_OFF_EXPIRE (§11).
  6. Prove apply → approve on a test employee (§12–13).

2. Big picture — configure then use

💡
Publishing ≠ balances
Publishing a policy activates eligibility and accrual rules. Tracopus does not invent opening balances. HR must import (or Adjust) balances, or wait for the monthly accrual job after go-live.

5. How to create / publish a new leave policy

Primary console: Admin → Leave admin → Global Policy Center.

  1. Create or select a jurisdiction

    Examples: IN, IN-KA, IN-MH, AE. Used for resolve, holiday calendars, and working-day scope.

  2. Apply a country / CFA template into a draft

    Choose CFA-IN-KA, CFA-IN-MH, CFA-IN-HR, CFA-IN-TN-CBE, or a blank draft. Edit entitlements, accrual, carry-forward, and special-leave JSON while unpublished.

  3. Simulate / Policy Test Lab

    Dry-run resolve for a sample employee. Lab scenarios may gate publish. Open /admin/leave/policy-test-lab.

  4. Assign holiday calendar key

    Key must match People → Holidays location keys (e.g. IN-KA).

  5. Configure working-day rules

    Team default, jurisdiction pattern (e.g. Mon–Fri or Sun–Thu), or employee override.

  6. Publish the version

    Published versions are immutable. To change rules later, clone a new draft and publish again. Publish activates accrual eligibility — it does not create balances.

flowchart TD
  J[Jurisdiction] --> T[Apply template]
  T --> D[Edit draft version]
  D --> S[Simulate / Test Lab]
  S --> H[Holiday key + WDR]
  H --> P[Publish]
  P --> R[Accrual + eligibility live]

APIs (for automation / support): jurisdictions POST /api/v2/leave/global/jurisdictions · apply template POST /api/v2/leave/global/templates/{id}/apply · simulate POST /api/v2/leave/global/simulate · publish POST /api/v2/leave/global/versions/{versionId}/publish.

6. Supported leave policies — how each is configured

PL means Privilege Leave (earned) — not paternity. Paternity is PATERNITY.

CodeNameHow to configureKey runtime rulesStatus
PLPrivilege Leave GLP version entitlements + monthly accrual; CF max in rules Fiscal Apr–Mar; CF max 45; excess LAPSE (or ENCASH if re-published) Shipped
CLCasual Leave Location pack entitlements (MH/HR/TN); no CF Lapses at fiscal year end; not in KA pack Shipped
SLSick Leave Location pack (KA/HR/TN); document rules for medical proof Medical certificate when ≥3 days; no CF Shipped
MATERNITYMaternity specialLeave[] in published GLP; FE child # maps days Female; min 80 service days; 182/182/84/84; proof; auto end from start Shipped
PATERNITYPaternity Special leave rules in GLP Male; 5 consecutive days; window 7 days before or 45 after event Shipped
MSLMilestone Leave Tenure grant rules in GLP Grant at 5/10/15/20y; 5-day block; partial use forfeits remainder Shipped
WWLWellness Leave KA female special in CFA-IN-KA 1 day/month; ±3 day apply window; lapses last working day of month Shipped
COMPOFFCompensatory Off Comp-off policy + attendance credit coupling Weekend/statutory ≥6h or weekday >15h; expire 90 days Shipped
FLOATINGFloating Holiday Floating catalogue + calendar-year budget Employee picks published option; Jan renew credits entitlement Shipped
UNPAID / ULUnpaid / LOP Catalog type; LOP coupling where enabled No entitlement balance required in typical setups Shipped
ADOPTION / MISCARRIAGESpecial stubs Catalog only until HR confirms days Entitlement days TBD Stub

Always needs approval

Leave requests always go through approval — even when attendance auto-approves for some bands.

Two leave years

Earned leave uses fiscal Apr–Mar. Floating holiday budget uses calendar Jan–Dec.

Server trusts day count

Create/submit recalculate numberOfDays from working week + holidays. Half-day = 0.5.

Classic fallback

If Global Leave is off, use /admin/leave-policies type catalog; accrual falls back to classic policy.

Holidays

  1. Create holidays in People → Holidays with a Location key (e.g. ["IN-KA"]).
  2. Assign that key to the jurisdiction in Global Policy Center → Holiday calendars.
  3. Optional: publish Legal Calendars so official holidays sync into People holidays.

9. Opening balances, Adjust, and dry-run

Canonical page: Admin → Employee leave config (/admin/employee-leave-config).

  1. Select the team in the header filter so employees load.
  2. Download OB template (Opening balance template panel / header button). Rows are employee × leave type (PL/CL/SL by location). entitlementAmount and amount start blank — fill from ZingHR / HR export only.
  3. Dry-run import (never skips this)

    POST /api/v2/admin/data-import/leave-balance?userTeamId={team}&actorId={you}&dryRun=true

    Body may also include "dryRun": true (query wins). Dry-run validates only — no writes. Fix failures from reportCsv / results[].

  4. Live import — same endpoint with dryRun=false only after dry-run is clean.
  5. Single employee correction — select person → Adjust balance (opening entitlement and/or +/− available days) with a reason. Adjustments of 5+ days require a second confirmer employee id.
  6. Spot-check balance cards, then prove apply on People → Leaves.

CSV columns (template)

userTeamId, employeeId, empCode, location, suggestedPack, leaveTypeCode, leaveTypeId, entitlementAmount, amount, comment

Aliases accepted: PAT→PATERNITY, MAT→MATERNITY, COFF→COMPOFF.

flowchart TD
  AP[Published policy] --> AJ[LEAVE_ACCRUAL job]
  AJ --> BL1[Ledger credit ACCRUAL]
  HR[OB import / Adjust] --> BL2[Ledger ADJUST_HR]
  BL1 --> UI[Visible on Leave Management]
  BL2 --> UI

10. Make sure leaves are assigned to every employee

“Assigned” means each active employee has: (1) a resolved published policy / jurisdiction, (2) leave type balances on the ledger, (3) correct holiday + working-day resolution.

  1. Confirm published policy for the team / jurisdictions covering all work locations.
  2. Assign jurisdictions (and WDR overrides if needed) for employees whose location differs from team default.
  3. Bulk OB import for cutover so every employee × PL/CL/SL row exists — do not invent amounts.
  4. For new joiners after cutover — either Adjust on hire, include them in a follow-up import, or rely on monthly LEAVE_ACCRUAL once entitlement rules apply.
  5. Verify coverage — on Employee leave config, sample employees across locations; KPI strip shows low-balance / pending signals.
  6. Smoke apply as 2–3 employees from different packs (e.g. KA vs MH) before broad rollout.
⚠️
Empty ledger after publish is expected
Until HR imports opening balances or accrual runs, employees correctly see zero available days and cannot submit (unless leaveAllowNegativeBalance is on).

12. How employees apply for leave

  1. Open People → Leave management.
  2. Review balance cards for the leave type you need.
  3. Click Apply leave. Choose type (PL/CL/SL/special/floating), start/end, half-day if allowed, reason, and required documents.
  4. Confirm day count (server recalculates — holidays and weekly offs are excluded).
  5. Submit. System validates overlap, working days, special rules, documents, and balance; then places a pending hold on the balance and notifies the approver.
  6. Track status on the same page (CREATED → SUBMITTED → APPROVED / REJECTED). Withdraw is allowed for draft/submitted only.

Floating: you must pick a published catalogue option. Maternity: child number maps duration. Comp-off: uses credited bank entries with expiry.

13. Leave request approval process

flowchart TD
  C[CREATE draft] --> S[SUBMIT]
  S --> H[Reserve PENDING_HOLD]
  H --> N[Notify approver]
  N --> D{Approve or Reject?}
  D -->|Approve| A[Debit DEBIT_APPROVE]
  A --> P[Promote TaskActivity LEAVE]
  P --> T[Optional attendance sync]
  D -->|Reject| R[Release hold + comment]

Who can approve

  • Reporting manager with approveTeamEnabled — via ApprovalAuthorityService.canAct(..., LEAVE).
  • Delegate when approval delegation is enabled and scope includes LEAVE.
  • HR / admin where role policy allows acting in scope (see Approvals inbox / leave pending panel).

Where to approve

  1. People → Leave management — Pending approvals panel for requests in your scope.
  2. Workspace → Approvals (/workspace/approvals) when universal inbox is enabled.
  3. Approve or reject. Reject requires a comment; pending balance is released.
  4. On approve: ledger debit, promote leave days to timesheet TaskActivities, optional attendance LEAVE / HALF_DAY marks.

After approval — cancel / promotion failures

  • Cancel (after approve) credits balance back and reverses promotion where supported.
  • If timesheet rows are missing, check promotionStatus, GET /api/v2/leaves/.../promotion-failures, and schedule LEAVE_PROMOTION_RETRY. Manual: POST /api/v2/leaves/{id}/promote.

Accrual / CF / comp-off data flow

flowchart TD
  CRON[fs_schedule_model tick] --> GATE{leaveManagementEnabled?}
  GATE -->|No| SKIP[SKIPPED]
  GATE -->|Yes| TYPE{Schedule type}
  TYPE -->|LEAVE_ACCRUAL| RES[Resolve published GLP per employee]
  RES --> CRED[Ledger ACCRUAL periodKey=yyyy-MM]
  TYPE -->|LEAVE_CARRY_FORWARD| CF[Apply CF / lapse / ENCASH from rules_json]
  TYPE -->|COMP_OFF_EXPIRE| CO[Expire unused COMPOFF bank]
  CRED --> BAL[ts_employee_leave_balance_model]
  CF --> BAL
  CO --> BAL
  • Policy pick order (accrual): employee resolved published GLP → team published → classic ts_leave_policy_model.
  • Idempotency: re-running ACCRUAL for the same periodKey does not double-credit.
  • Missed accrual alert: CF job (days 1–3) can raise LEAVE_ACCRUAL_MISSED when the 1st-of-month job did not run.
  • Inspect source: GET /api/v2/leave/global/accrual-source?userTeamId= and GET .../resolve?userTeamId=&employeeId=.

Technical debugging playbook

  1. Confirm flags — org leaveAdditional + role modules for the exact team under test.
  2. Confirm policy source — accrual-source + resolve for a sample employee; ensure published version, not only draft.
  3. Confirm balances — balance cards + ledger rows; if empty, check import dry-run report or last ACCRUAL run.
  4. Confirm day count — holiday key assignment + WDR resolve preview; apply a range that spans a known holiday.
  5. Confirm approval path — actor must pass ApprovalAuthorityService.canAct for LEAVE; check delegation scopes.
  6. Confirm side effects — after approve, TaskActivity promotion status and attendance sync flag.
  7. Confirm schedulers — fs_schedule_model enabled + last_run; manually run ACCRUAL for a test team if safe.
💡
Ledger is the audit trail
Prefer reading ts_leave_balance_ledger_model over guessing from UI cards when balances look wrong. Every HR adjust, hold, debit, accrual, and cancel should leave a typed ledger event.
