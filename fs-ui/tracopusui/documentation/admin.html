Admin & Access

How permissions shape what you see in the Luxury UI — module menus, project scoping, timesheet date policies, and application configuration. Scenario pages document the same flags with step-by-step workflows in the Scenario User Guide.

Access overview

Tracopus uses role-based access control enforced on both client and server. The UI hides menus and actions you cannot use rather than showing disabled controls. Access is evaluated at multiple levels:

  1. Module level — can you see HRMS, Sales, or Project directories at all?
  2. Page level — which routes within a module appear in the sidebar?
  3. Persona level — which persona views you may switch into, and which pages each persona can open (org map + kill switches)
  4. Action level — create, edit, delete, assign, mark attendance, etc.
  5. Record level — project membership, team scope, shared vs private visibility
  6. Field level — timesheet date windows, report type availability

Mobile receives an encrypted access control payload on login; web evaluates permissions from the authenticated user session.

Project access

Team scope

Team selection filters on list pages limit data to projects and records associated with selected teams. Your default team appears in the sidebar company chip.

Project membership

Project details enforce membership and team rules:

  • Non-members may see read-only or denied views depending on shared visibility settings
  • Cross-team access without membership renders read-only project details
  • Members tab manages invitations, roles, and access chips

Shared vs private projects

Project list "Shared visibility" donut reflects how many projects are shared across teams vs restricted. Private projects appear only to members and elevated roles.

Create permissions

Create buttons on lists (projects, bids, POs, employees) and planner assign actions require explicit create permissions. Executive planner view is read-only when create is disabled.

Timesheet access rules

Managers with multi-employee timesheet permission can switch employees on the web Timesheet page header.

Application configuration

/hrms/appconfig — hierarchical configuration tree per team (admin access required).

What admins configure

  • Application configuration (org.json) — dropdown lists, service line trees, notification emails, feature toggles, personaNavigationAdditional
  • Access control (role.json) — module visibility, CRUD permissions, timesheet windows, report access, personaModules
  • Team-scoped overrides inherited from parent org nodes with lock/hide/inherit controls
  • Role bar for assigning role templates to org units during editing
  • Dedicated UIs: Admin → Roles (persona-first) and Admin → Persona navigation (simplified Turn off / Page access)

Reports & feedback permissions

Report types in the REPORT dropdown are filtered by permission — users only see reports they can run. Feedback template configuration and campaign launch similarly require elevated project permissions.

External feedback and invoice document routes (/document/…) use tokenized links that bypass full app auth for respondents while keeping responses scoped.
